# 审查系统毕业论文写作风格

适用于软件需求文档智能审查及相关软件工程课题的中文开题报告与毕业论文。本文从课题写作规范整理为可复用的风格指南，保留论证方法与原创示例，不附带原研究的文献库、实验数据或项目状态。使用者需提供自己的原始材料；本指南不是文献证据或学校格式规范。

## 1. 总体风格定位

采用**问题明确、方法可追踪、工程描述具体、结论受证据约束**的计算机应用研究写法。以“需求文档中什么问题难以判断—系统如何取得和组织依据—如何验证其效果—哪些情况仍不能处理”为主线。技术名词服务于解释方法，不以堆叠模型、框架和架构名称体现创新。

文风上吸收中文工程论文的问题分解、流程与模块说明，英文实证研究的研究问题和有效性威胁，以及综述论文的分类与比较。对原文中的笼统优越性表述、含混指标和缺少证据的性能主张，不予照搬。

## 2. 段落如何组织

一个段落围绕一个可辨认的中心判断展开。常用顺序为“对象与问题—已有证据或机制—适用条件—对下一步的含义”，不要求每段都套齐四项。描述现象、解释方法和讨论结果尽量分段，避免在一个长句中完成背景、贡献、数据、结果和展望。

**背景段示例（本次原创示范，非文献结论）：**

> 需求文档中的同一业务规则可能分散在不同章节，并以文字与流程图分别描述。审查这类规则时，需要先确定描述之间的对应关系，再比较其适用条件和约束是否一致。本课题拟保存文本片段与图中元素的来源，研究关联证据对辅助审查的作用。

这个段落只说明拟研究的问题和路径，没有虚构问题发生频率、检测提升幅度或产业损失。若要增加“某类缺陷普遍存在”等经验判断，须补充直接支持该判断的文献或调查数据。

## 3. 术语和语气

以“本文”“本研究”“所设计的系统”为主语，不频繁使用“我们认为”“笔者认为”。固定术语首次出现时解释含义，必要时给英文和缩写；之后统一使用同一名称。不要把审查、需求生成、需求分类、需求追踪、代码审查和形式化验证当作同义词。

| 用语 | 建议口径 |
| --- | --- |
| 审查发现 | 系统生成的待复核意见；经人工确认后才按实验标注规则计入正确发现。 |
| 依据/证据 | 能回到相应文档版本的文字片段或图中位置；位置存在与证据支持结论是两个评价层次。 |
| 一致性问题 | 在相同对象及适用条件下，两处或多处约束不能同时成立；单纯措辞不同不自动构成冲突。 |
| 完整性问题 | 相对于明确检查项和实际覆盖范围的疑似缺失；未检索到不等于原文不存在。 |
| 可解释性 | 具体说明解释对象、来源及评价方法，不作为天然可信的形容词。 |
| 显著提升 | 仅在有对应统计检验或明确统计依据时作统计意义表述；否则写具体差值和条件。 |
| 创新/贡献 | 描述你完成了什么以及证据，不使用“填补空白”“首次”替代已有工作比较。 |

“可以”“能够”要有范围。例如：“在已成功解析并具有来源编号的文本片段上定位”，比“能够准确理解所有文档”更可检验。承认边界不需要每句加“可能”；对于确定的实现和观测结果应直接陈述。

## 4. 开题报告与毕业论文使用不同的时态和证据

开题报告说明准备解决什么、为什么值得做、拟如何实现和验证。使用“拟构建”“计划比较”“将分析”，不写尚未发生的结果。预期成果宜写系统、数据说明、实验与分析材料，不预先承诺任意准确率。

论文描述已经完成且可核验的工作，使用“构建了”“实现了”“在所用测试集上得到”。未完成内容放在限制或展望中，不能借助过去时把计划变成结果。文献中的实验数字只属于相应作者，不能混入本系统实验摘要。

**开题方法示例（原创）：**

> 本课题拟比较模型直接审查、固定检索增强审查与具有补充检索过程的审查方法。在保持测试样本和问题判定规则一致的条件下，记录检测结果、引用依据、工具调用次数及耗时，分析补充检索的收益与代价。

**论文结果句式（占位示例，不含真实实验数据）：**

> 在〔数据集及划分〕上，方法A的〔指标〕为〔实测值〕，方法B为〔实测值〕。差异主要出现在〔缺陷类型〕；对于〔失败类型〕，方法A仍存在〔观测到的限制〕。

占位符必须在正式论文中以真实结果替换；没有数据时删除结果句，不能填入文献中的数值。

## 5. 章节组织建议

最终结构服从学校模板，下列仅为与当前研究任务相符的内容组织建议。

1. **绪论。** 场景与具体问题、研究现状、现有方法边界、研究内容与文章结构。技术热度最多用作背景，不能成为唯一动机。
2. **相关概念与技术。** 只介绍后文实际用到的概念和技术，例如需求质量定义、检索机制、图谱关系与图文表示；每项技术说明其在方法中的用途。
3. **需求分析与总体设计。** 描述用户操作、审查输入输出、状态、来源追踪及系统边界。图中模块名称与正文保持一致。
4. **审查方法与关键实现。** 按实际采用的处理环节展开，例如文档解析、要素关系抽取、证据检索与补检、判断与校验、人工复核。每节说明输入输出、关键规则、失败处理和选择依据。
5. **实验与结果分析。** 数据与许可、标注、划分、研究问题、基线、参数、指标、结果、消融、错误案例及有效性威胁。功能测试与方法实验分别呈现。
6. **总结与展望。** 对照研究问题总结已完成内容及证据，具体说明实际遇到的限制，例如中文图文样本不足、模型波动或适用范围有限，再提出后续工作。

当方法篇幅较大时，可将系统实现单列一章。无需为了“看起来像硕士论文”人为拆章；本科论文的完整性来自闭环证据，而不是章节数量。

## 6. 方法、图表和案例的表达

方法节以输入输出契约开头。例如，图谱关联要说明输入是哪一文档版本、实体如何产生、关系如何校验、输出如何回链；只列数据库与模型名称不足以说明方法。流程图中的每一步都应能在正文找到说明。

用一个授权或自制需求示例贯穿各阶段：展示原文与流程图位置、候选节点关系、检索到的片段、判断条件、待复核结论和人工处理。若示例用于教学而非真实实验，明确标注“说明性示例”。不要仅展示正确案例，也选一个检索遗漏或图文识别错误案例解释限制。

表格注明对象、样本数、指标方向、单位、模型和实验条件。对照实验与消融实验分开；引用别人的表格时标来源，重新计算时标“根据原文数据计算”及计算规则。表后解释差异及局限，而不是把每个数值重复一遍。

架构图解释职责和数据流，流程图解释执行和分支，结果图解释比较。界面截图只支持“系统如何操作与展示”的说明，不用于证明算法有效。多模态能力必须展示图中元素如何参与关联与判断，不能用附了一张图片替代方法说明。

## 7. 实验论证的写法

每个研究问题对应可重复的比较，先说明变量和判定规则再展示结果。模型版本、提示模板、检索设置、任务预算、失败统计与重复次数应按实际记录填写。训练/开发与测试按文档或项目来源控制信息泄漏，不能只因段落文本不同便认定样本独立。

结果部分报告观察，讨论部分解释可能原因。若没有消融或独立对照，不把提升全部归因于图谱或主动检索。生成解释“流畅”与“证据充分”分别评价；人工采纳也受界面、任务和使用者影响，不自动等于客观正确。

对负面结果直接描述：例如主动补检增加了耗时却未改善某类问题，或图文关系抽取错误造成误报。只有记录这些条件，结论才适合被后来研究引用。

## 8. 文献引用和数字表达

引用紧跟所支持的判断，避免一个段落末尾挂多个文献却无法区分证据来源。优先引用原始研究描述其方法和结果，使用综述支持分类或研究趋势；没有读到原研究时，不把综述的转引写成自己已核对原研究。

严格区分Precision、Accuracy、Recall、F1、F2、BLEU及主观评分；保留数据集、模型与平均方式。原文摘要与表格矛盾时说明差异，不选择对自己最有利的版本。具体处理见[原文核验与文献卡](source-verification.md)。

同一研究的学位论文与相关期刊论文可能共享方法或数据，不能当作独立多项研究夸大证据强度。研究现状要同时交代直接相关和间接借鉴关系，尤其不要把需求生成或代码审查的提升外推为本系统审查提升。

## 9. 定稿前的风格自检

- 每节是否有一个明确问题，而不只是技术介绍或功能罗列？
- 每个性能或普遍性判断是否有原文定位或本系统数据？
- 是否分清作者结论、本次整理分析和本课题假设？
- 是否把计划写成完成，把界面运行写成算法有效，或把准确率与精确率混用？
- 方法输入输出、适用条件、失败处理及来源版本是否清楚？
- 实验是否报告不占优的结果，结论是否保留样本和任务范围？
- 所有占位符、临时文献编号、未确认题目和未经核实的数字是否已处理？

最终应让读者看清“研究了什么、为什么这样设计、证据支持到哪里”。保持具体、克制且可核验的表达，比模仿原文的长句或强烈评价词更适合本课题。
